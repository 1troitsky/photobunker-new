## 3. Статусы и честность

Использовать только эти статусы:

- `CONFIRMED` — факт проверен на текущем SHA/окружении.
- `IMPLEMENTED` — код существует, но пользовательский результат не подтверждён.
- `OWNER FAILED` — владелец проверил на реальном устройстве и сообщил дефект; тесты не могут повысить этот статус.
- `PARTIAL` — работает только часть сценария.
- `NOT RUN` — проверка не выполнялась.
- `BLOCKED` — опасная операция намеренно выключена до доказательства безопасности.
- `ACCEPTED` — только владелец подтвердил результат.

Нельзя писать «готово», если есть только код, unit test, Playwright или HTTP 200. Для UI важна реальная мобильная приёмка. Для безопасности нужны отдельные технические доказательства.

## 4. Как работать

1. Выбрать **один** пункт из quick-task очереди `docs/16-*`/`ts_and_ux.md`.
2. До кода воспроизвести дефект и зафиксировать текущий экран/маршрут/время/ошибку без приватных данных.
3. Сделать минимальный вертикальный fix. Не начинать параллельный редизайн пяти подсистем.
4. Сначала проверить затронутый сценарий; широкую регрессию запускать после работающего результата, а не вместо реализации.
5. Для mobile UI сделать production screenshot/видео на viewport, близком к реальному телефону, и проверить реальное устройство, когда оно доступно.
6. Обновить `docs/15-*` и `docs/16-*`: SHA, что изменено, PASS/FAIL/NOT RUN, что должен проверить владелец.
7. Коммитить и push после каждого законченного шага. Не force-push и не менять `main` без прямой команды владельца.
8. После каждого задания обязательно отправлять владельцу итоговый отчёт: исходная проблема и критерий, фактические изменения, затронутые файлы, commit/push/deploy и release ID, точные результаты проверок, всё `NOT RUN`/непринятое и конкретный сценарий проверки владельцем. Не завершать работу молча и не заменять отчёт фразой «готово».

Отмена формы (`×`, Back, Cancel) не должна сохранять или создавать объект. Настройки, для которых владелец потребовал мгновенное сохранение, не должны показывать ложный dirty-state/unsaved dialog.

## 4.1. Обязательные инструменты Codex (OpenSpec, UI/UX Pro Max, Playwright MCP, Lighthouse CI)

**Обязательность определяется типом работы, а не желанием агента.** Не запускать все инструменты и полный test suite на каждой задаче. Не расходовать время/лимиты на повторную установку, общий аудит или тестирование чужих модулей без запроса владельца.

**Проверка доступности — один раз в новой рабочей среде или при реальном сбое инструмента**, не в каждом сообщении. Для Codex использовать существующие глобальные/project Skills, реальный MCP-сервер и CLI. Не путать запись в `package.json` или упоминание в документации с доступностью инструмента в текущей сессии. Если инструмент недоступен — явно указать `NOT AVAILABLE` / `NOT RUN`, не имитировать его вызов и не утверждать `PASS`; не устанавливать пакеты и не менять настройки без разрешения владельца.

| Инструмент | Обязательный случай | Что является доказательством применения |
| --- | --- | --- |
| **OpenSpec** | **Перед каждой реализацией**: использовать уже согласованный quick-task ID/спецификацию, уточнить scope и критерий приёмки. Для новой функции, многокомпонентного изменения или неоднозначной архитектуры — создать/обновить change через официальный `openspec-propose`, затем выполнять через `openspec-apply-change` после согласования. Для маленького исправления использовать существующий task без раздувания новых proposal. | Название существующего task/change, какой scope и критерии применены; при наличии change — ссылки на его артефакты. |
| **UI/UX Pro Max** | **Каждое изменение UI/UX**: layout, navigation, controls, typography, responsive, accessibility, PWA screen behavior. До правки прочитать доступный `ui-ux-pro-max/SKILL.md`, воспользоваться его релевантными рекомендациями и сверить с `ts_and_ux.md` и существующими дизайн-правилами. | Конкретные применённые UI-принципы и затронутые экраны. Skill не заменяет решения владельца. |
| **Playwright MCP** | **После каждого изменения поведения интерфейса**, когда доступен тестовый URL/браузер: открыть **действующий** `compat/assignment-release/` runtime и пройти конкретный изменённый сценарий, проверить desktop + узкий mobile viewport, ошибки консоли и при необходимости сохранить скриншот. | Реальный запуск MCP, URL/viewport, сценарий, PASS/FAIL и путь к артефакту. `@playwright/test` ≠ Playwright MCP; если использовался CLI, назвать его отдельно. |
| **Lighthouse CI** | **Когда меняется производительность, загрузка, bundle, rendering или по явному запросу на perf/a11y**. Измерять production-build релевантного runtime и сравнивать с сопоставимым baseline, если он есть. | Запущенная команда, URL/build ID и измерения; без baseline не заявлять об улучшении. Не запускать ради обычного исправления текста, PIN-логики или прочего нерелевантного scope. |

**OpenSpec в репозитории:** если `openspec/` и Codex Skills (`.agents/skills/openspec-*/SKILL.md`) отсутствуют, это не «готово» только потому, что CLI установлен глобально. Перед первой spec-driven задачей сообщить владельцу, что проектную инициализацию нужно выполнить **один раз в корне этого worktree** штатным `openspec init` для Codex; получить разрешение на создаваемые файлы, проверить diff. Не инициировать OpenSpec в `compat/assignment-release/` как во втором независимом проекте.

**UI/UX Pro Max:** допускается уже установленный глобальный `~/.agents/skills/ui-ux-pro-max/SKILL.md`; не копировать его в репозиторий без необходимости. Если он не загружается в используемом клиенте Codex, честно отметить ограничение вместо выдуманного результата.

**Порядок на одной задаче:** scope/OpenSpec → применимый UI/UX Skill → минимальная правка в правильном runtime → узкие проверки через Playwright MCP (для UI) и Lighthouse CI (когда уместно) → сравнение с критериями → отчёт из §4. Документация и checkbox обновляются **после** доказанного результата; `ACCEPTED` — исключительно после приёмки владельцем на устройстве.

**Запрет:** считать задачу выполненной из-за галочек в `tasks.md`, количества пройденных тестов, скриншота без проверки сценария или успешного `git commit`. Если результат не проверен — `IMPLEMENTED`/`NOT RUN`, а не `CONFIRMED`/`ACCEPTED`.

## 4.2. Инженерный стоп-кран: качество важнее количества кода

Это **обязательный контракт для каждой задачи**, включая простые исправления. Рабочая единица — один пользовательский сценарий с доказанным результатом, **не** один коммит, набор файлов, чекбокс или количество тестов.

1. **Сначала найти готовое.** Прежде чем писать компонент, CSS-паттерн, состояние, сервис или алгоритм, проверить существующие реализации и зрелые совместимые библиотеки. Кратко зафиксировать выбор: `REUSE` / `LIBRARY` / `CUSTOM` и причину. Не изобретать стандартный UI и не добавлять dependency без подтверждённой совместимости и нужды. Новые зависимости — только с разрешения владельца.
2. **Одна реализация — один владелец ответственности.** Бизнес-правила не размещать в Vue view; криптография, storage, API, ACL, TTL — в существующих сервисах. Не копировать компоненты, стили, обработчики, сервисы и состояние между экранами. При обнаружении второго экземпляра одного паттерна переиспользовать/выделить общий узел **в пределах данной задачи**, не делать глобальный рефакторинг.
3. **UI — из единой системы.** Применять текущие tokens, цвета, шрифты, отступы, компоненты и mobile safe-area. Переиспользовать Button/Input/Select/Dialog/Sheet/Toast/PinInput и др. из принятой UI-основы, если они уже существуют. Если основы ещё нет — **не объявлять её установленной** и не строить новую втайне; для нового стандартного элемента кратко предложить существующую библиотеку (напр. Reka UI), показать trade-off и получить решение владельца. SVAR/VueFinder — только кандидаты для Browser, не автоматически разрешённые зависимости. Не добавлять локальные CSS-костыли для компенсации общего layout-дефекта.
4. **Перед правкой назвать критерий, после правки доказать.** Внутренне сверить: конкретный дефект, существующая точка реализации, минимальные изменяемые файлы, один воспроизводимый пользовательский сценарий, pass/fail. Для UI проверить на production-build реального runtime через Playwright MCP и показать владельцу доказательство (сценарий, viewport, скриншот/видео), а не только утверждение `PASS`. Конкретные безопасные unit/contract checks — по изменённой логике; **не запускать общий suite без причины**.
5. **Не гнаться за зелёной галочкой.** При FAIL исправлять **первопричину**, не менять требования, тест, статус или документацию ради видимости успеха. Не скрывать дефект новыми слоями CSS, fallback или таймером. Если две целевые попытки не устранили один дефект либо изменение выходит за согласованный scope, **STOP**: предоставить владельцу причину, проверенные факты и один минимальный следующий шаг. Самостоятельно не начинать третью попытку, переписывание или установку новых инструментов.
6. **Отчёт должен быть проверяемым и коротким.** `Task ID | reuse/library/custom + причина | diff/commit | проверенный сценарий | FAIL/NOT RUN | что осталось владельцу`. Скриншоты и тесты без связи с пользовательским результатом не считаются доказательством.

**Важная граница автоматизации:** инструкции выше не заменяют реальный CI и приёмку. GitHub workflow `.github/workflows/pb2-draft-quality.yml` ориентирован прежде всего на **корневой PB2**, а работающий сейчас runtime — `compat/assignment-release/`. Не выдавать green CI PB2 за проверку Assignment Release. Отдельного обязательного quality gate для активного runtime пока нет: помечать это честно, не обещать автоматического запрета некачественного merge/deploy.

## 5. Технические инварианты

- Anonymous key-only identity; email/phone — только необязательные скрываемые поля профиля, не credentials.
- Local-first: shell и локальные данные не ждут HTTP; capture сначала шифруется и durable сохраняется, синхронизация позже.
- Фото, GPS, EXIF, PIN, ключи и токены не попадают в logs, URLs, analytics или plaintext persistent cache.
- Фото не экспортируется в системные Photos/DCIM автоматически.
- UI не должен напрямую владеть raw DB/HTTP/crypto/S3 бизнес-логикой; целевые границы — domain/application/infrastructure/ui.
- Photo, Photo Card, Assignment, Team, Note и Browser collection — разные сущности и scopes.
- TTL определяется выбором пользователя и пределами тарифа; зафиксированный при capture effective TTL нельзя незаметно продлевать.
- App PIN и emergency PIN — разные секреты, но вводятся через один визуально неразличимый экран согласно `ts_and_ux.md` и `docs/16-*`.
- `_old/**` и `1troitsky/photobunker` — только read-only evidence. Не редактировать, не форматировать, не stage/commit.

## 6. Запреты на окружение и данные

Без прямого подтверждения владельца запрещены:

- `docker system prune`, `docker compose down -v`;
- удаление containers/images/volumes и данных OrbStack/Colima;
- `migrate:fresh`, `db:wipe`, сидеры, restore БД;
- очистка PWA site data, IndexedDB, OPFS или пользовательского cache, если это может удалить фото/ключи;
- широкие destructive Local Delete/Emergency операции без preflight, recovery proof и owner approval.

Если порт занят, менять порт проекта или аккуратно останавливать только точно идентифицированный конфликтующий контейнер после согласования. Никогда не уничтожать чужой стек.

## 7. STOP

Остановить затронутый сценарий и зафиксировать проблему при любом из условий: plaintext photo/metadata на диске; потеря unsynced ciphertext; late ACK воскрешает удалённое; ACL/TTL обходится; expiry оставляет доступные файлы/metadata; ключ/PIN/GPS утекает; production camera ломается; destructive PIN может удалить данные без доказанного восстановления.
