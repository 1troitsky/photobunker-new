# PIN: причины и изменения — 2026-11-06

Объём согласован владельцем: стабильный ввод, понятное восстановление, последняя точка, переход без Welcome, выбранная задержка блокировки, четыре шага настройки PIN уничтожения. Текущий результат до приёмки — `IMPLEMENTED`; обычный PIN и UI настройки должны быть проверены владельцем на телефоне. Экстренная активация остаётся `BLOCKED`: `emergencyDeletionAvailable=false`, независимое сохранение cloud backup не доказано. Форма не объявляет PIN установленным после одного лишь ввода частей.

## Причины и исправления

- `PasscodeInput` очищал model до отрисовки N-й точки. Теперь native input очищается синхронно для следующей части, а локальный счётчик показывает все N точек до следующего ввода; секрет не сохраняется в storage. Убрана анимация закрашивания. Очередь сегментов и PBKDF2 verifier/lockout не менялись.
- Lock form центрировалась в `100dvh`, имела большой heading margin и автофокус со скроллом. Теперь верхняя привязка без центрирования/резерва dock и `preventScroll` только для lock screen. Другие формы сохраняют обычный scroll-to-focus. Восстановление — короткий RouterLink с иконкой и подчёркиванием.
- Welcome мог смонтироваться после снятия lock, пока распознанная identity/route ещё переходила к рабочему экрану. App скрывает гостевой landing для известного аккаунта, заранее перенаправляет подтверждённую/offline identity и показывает общий skeleton на pending navigation. Защищённые компоненты по-прежнему ждут identity и PIN; локальный account не считается API grant.
- App timer и crypto lifecycle расходились: visibility делал warm-lock независимо от delay, pagehide уничтожил бы ключи сразу. Теперь один deadline владеет App PIN: первый hide фиксирует wall+monotonic time, повторный hide/pagehide не продлевает срок; resume проверяет срок даже при остановленных OS timers, rollback закрывает доступ. В trusted-device grace остаются уже открытые локальные ключи; при deadline App выполняет существующий hardLock. Candidate/untrusted protection не получает эту льготу. Полный reload снова требует PIN.
- Background read-proof refresh не запускается при hidden. При возврате transport/5xx failure сбрасывает remote read token, сохраняя прежние trusted local keys; 401/403 и ошибки proof по-прежнему закрывают ключи. Нового remote grant, изменения TTL или обхода crypto boundary нет.
- Emergency setup показывал два поля по 12 точек и диапазон 4–6. Теперь при отсутствии App PIN только предложение сначала установить его; иначе четыре последовательных шага по точному N: первая/вторая/повтор первой/повтор второй. Каждая новая часть сравнивается с действующим verifier без изменения счётчика попыток; повторы проверяются отдельно. Совпадение частей друг с другом разрешено. Cancel, уход с панели, смена owner/device/длины PIN и unmount очищают draft. Обычные поля подтверждения прежнего PIN также используют фактическую длину. Legacy normal PIN длиннее поддерживаемого emergency-контракта требует сначала сменить обычный PIN; существующий verifier не удаляется.

Реальные iOS/Android screen-off, OS keyboard, suspended/BFCache PWA, crypto worker/key retention на hardware, production private unlock и emergency registration/deletion/recovery — `NOT RUN`. Никакие destructive triggers, wipe, сбросы пользовательского storage или изменения verifier существующего аккаунта не выполнялись. Существующая пользовательская правка `ts_and_ux.md` не включается в этот commit.

Проверка владельца: Security → App PIN → 5 минут → Lock → быстро ввести PIN → открыть фото → свернуть/вернуться раньше 5 минут, затем повторить после 5 минут; проверить системную клавиатуру, все точки и отсутствие Welcome. Emergency → четыре шага с длиной обычного PIN; активация должна оставаться явно недоступной до закрытия backup blocker.
