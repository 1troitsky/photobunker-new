# 03. Хранение фотографий и жизненный цикл файлов

**Статус:** частично утверждённая архитектура / остальные вопросы OPEN.  
**Решения владельца от 2026-10-28:** ST-01 (гибрид), ST-02/03 (режимы и assignment policy), ST-05/06 (одна миниатюра, без отдельного постоянного preview), ST-09 (срок 24 ч — 45 дней и полная очистка), ST-12/13 (metadata и шифрование). Для первоначального S3-адаптера выбран Garage; смена S3-провайдера не меняет бизнес-логику.

Этот документ — центральный источник истины по жизненному циклу фотографий нового PhotoBunker. **Roadmap и Issues подготовлены; реализация не начата.** Ни одно неутверждённое предложение ниже не является разрешением на изменение API или удаление пользовательских файлов.

## 1. Утверждённые принципы

1. Фото сохраняется **сначала локально на устройстве**, затем синхронизируется с **S3** отдельно, в фоне. Сеть не блокирует допустимые локальные действия. Начальная S3-compatible реализация — **Garage**, за отдельным S3 adapter; возможна замена провайдера без изменений Camera/Gallery/Editor.
2. **Метаданные не запекаются в единственный источник истины внутри файла.** При съёмке создаётся отдельная запись в локальной БД, связанная с фотографией; в дальнейшем она синхронизируется с серверной БД согласно модели прав и E2EE. Пиксели/зашифрованные файлы хранятся отдельно от записей метаданных.
3. На локальном устройстве фото и чувствительные метаданные **сохраняются только в зашифрованном виде**. Открытый снимок допустим только как кратковременное содержимое памяти при съёмке, просмотре и редактировании; он **не записывается** как нешифрованный файл, cache, export или temp.
4. **Ни один снимок не должен автоматически попадать в системную галерею** телефона/компьютера (Photos, «Фото», DCIM, camera roll). Внутренняя галерея PhotoBunker — собственное защищённое представление, не системная фототека. Любой будущий ручной экспорт за пределы приложения — отдельная ещё не согласованная функция.
5. **Политика задания определяет обработку и сохранность original** по одному из трёх режимов. Значение по умолчанию — «перезаписывать оригинал». При отсутствии задания также действует режим по умолчанию.
6. **Срок жизни каждой фотографии ограничен:** от **24 часов до 45 дней** по заданию; для снимка сохраняется эффективный `expires_at`. По достижении срока прекращается любой доступ и автоматически удаляются **все** связанные изображения, originals, edited variants, thumbnails, exports, shares, blobs, локальные записи и серверные metadata/Photo rows. Не создавать неучтённые копии, постоянные previews и вечные архивы версий. Ошибка диска/браузера не должна повреждать последнюю ещё действительную копию.

## 2. Режимы сохранения изображения (ST-02 + ST-03 — DECIDED)

Это свойство **задания**, применяемое к каждому сделанному в его рамках снимку. Для личного фото без задания — тот же режим по умолчанию.

| Режим | Пункты UI задания | Съёмка | После сохранения отредактированного изображения | Статус |
| --- | --- | --- | --- | --- |
| **1 — Исходный снимок без повторного сжатия** | «Сохранять оригинальный снимок без сжатия» | Сохранить полученные от камеры исходные данные **без дополнительного сжатия/перекодирования приложением** | Исходный объект неизменен; отредактированное представление отдельно (детали OPEN) | **Показывать в интерфейсе отключённым**; недоступен для выбора в первой версии |
| **2 — Сжатый оригинал отдельно** | «Хранить сжатый оригинальный снимок отдельно» | Сжать/оптимизировать исходный снимок, сохранить сжатый оригинал | Сжатый оригинал остаётся отдельно, отредактированное изображение сохраняется отдельно | Доступен |
| **3 — Перезаписывать оригинал** | «Перезаписывать оригинал» | Сжать/оптимизировать исходный снимок и сохранить как единственный текущий основной файл | Новый отредактированный результат **заменяет** текущий основной файл; старый файл физически удаляется после безопасного переключения | **Доступен; выбран по умолчанию** |

**Уточнение терминов:** «без сжатия» в режиме 1 означает **не производить дополнительную компрессию в приложении**. Браузерная камера может уже выдавать JPEG или другой сжатый формат. Получение сенсорного RAW/несжатого кадра не гарантируется стандартным web camera API и **не обещается** пользователю. Режим 1 не должен выглядеть доступным, пока его реальное поведение не реализовано и не проверено.

**Режим 2**: «отдельно» означает две логически и физически различимые долговременные копии **только после появления редактирования**: сжатый исходник и актуальный обработанный результат. До первого редактирования не создавать фиктивную вторую полноразмерную копию. Постоянную историю многих отредактированных версий не считать автоматически разрешённой.

**Режим 3**: обычное редактирование не должно оставлять старый master или несжатый источник навсегда. Сохраняется актуальный обработанный master. Если редактирования нет, хранится только оптимизированный master. Старое изображение удаляется **после** успешной защищённой фиксации нового; краткий временный пик из двух зашифрованных blobs допустим, чтобы не уничтожить фото при ошибке записи.

Нужно сохранять **режим, действовавший при съёмке**, вместе с фото и ревизией задания. Последующее редактирование задания **не должно задним числом изменять режим существующих фото** без явно согласованной операции и прав. Изменение политики задания для новых фото — отдельно от старых.

**Не выбирать** режим по наличию конкретного UI-экрана. Единственный источник решения — сохранённая политика capture на момент съёмки. Backend должен валидировать поддерживаемые значения; скрытый/disabled пункт фронтенда сам по себе не является защитой от API-вызова.

## 3. Модель данных: метаданные отдельно от файла (ST-12 — DECIDED)

На момент съёмки у PhotoBunker появляются:
- **Photo record**: стабильный ID, привязка к владельцу/устройству/заданию, ревизия задания и выбранный режим, время/состояние, ссылки на зашифрованные assets, локальная запись для синхронизации.
- **Photo metadata record**: связанные с ID отдельные структурированные метаданные съёмки и пользовательские поля (точный набор полей, EXIF, GPS, видимость — OPEN).
- **Photo encrypted asset(s)**: зашифрованные байты изображения, физически отдельно от записей БД.

Сначала фиксируется согласованная локальная операция сохранения **в зашифрованном виде** (байты + метаданные + запись синхронизации); только после её успешного завершения можно показать «Сохранено на устройстве». В фоне выполняется подтверждаемая идемпотентная синхронизация в S3 и серверную БД. Сбой сети не удаляет локальную несинхронизированную фотографию.

«Отдельная БД» означает **структурированное хранение метаданных отдельно от файлов изображения**, а не требование немедленно писать их в PostgreSQL через сеть при нажатии затвора: это противоречило бы принятому local-first. На устройстве — локальная БД; на сервере после синхронизации — база Laravel/PostgreSQL. Какие именно серверные поля доступны в открытом виде для ACL/индексов, а какие хранятся как encrypted metadata, — OPEN для безопасности и API-контракта. Никакие приватные GPS/описания/EXIF нельзя произвольно класть в открытый Laravel DTO или localStorage.

**Идентификаторы и события:** снимок, метаданные и зашифрованные объекты связаны одним ID фото и проверяемыми ревизиями; повтор после lost ACK не создаёт второго снимка. Photo Browser и Photo Card читают разрешённые проекции канонической metadata record, не заводя параллельные копии метаданных без необходимости.

## 4. Безопасный путь камеры (ST-13 — DECIDED)

```text
Camera API -> кратковременные байты в памяти
  -> применить режим 1/2/3 (оптимизация в памяти, если предписана)
  -> зашифровать изображение и чувствительные метаданные
  -> сохранить зашифрованные blobs + metadata record + outbox на устройстве
  -> показать фото во внутренней защищённой галерее PhotoBunker
  -> позднее: синхронизировать ciphertext в S3 и разрешённые данные в Laravel
```

**Никогда** не вызывать автоматическое сохранение в Photos/DCIM, media library или системный camera roll. Использование `getUserMedia`/browser capture допустимо, если данные остаются только в изолированном процессе приложения до шифрования. Не использовать как pipeline захвата сценарии, которые автоматически записывают в системную медиатеку.

**Требования к browser/PWA реализации:** исследовать особенности iOS/Android Safari/Chrome, возможные OS/browser temporary copies и ограничения camera API, а не обещать абсолютный контроль над скрытыми внутренними буферами ОС. Наш код не создаёт/сохраняет plaintext файлы, превью или нешифрованные database entries. В памяти расшифрованные данные уничтожаются/освобождаются по возможности при закрытии/блокировке; визуальные URL/object URL отзываются. Ни один пользовательский путь не вызывает системный диалог «сохранить в галерею» автоматически.

Системная галерея **не равна** внутренней вкладке «Фото» PhotoBunker: внутри приложения снимки отображаются из доступных зашифрованных assets после необходимой разблокировки.

## 5. Надёжная замена master без накопления мусора

Поскольку файлы и записи локальной БД могут жить в разных API, нельзя обещать физически общую атомарную транзакцию. Нужен восстанавливаемый переход:
1. Создать **зашифрованный временный новый master** с ID/размером/хэшем и привязкой к photoId.
2. Проверить, что он полностью записан и пригоден для последующего чтения/дешифрования.
3. Переключить **канонический указатель на asset** (с ревизией) в локальной БД только при сохранении прежней корректной ссылки до этого шага.
4. Пометить старый asset на удаление; удалить его физически и повторять cleanup после перезапусков.
5. Аналогично синхронизировать в S3: новым объектом + подтверждением, с CAS/ревизией, затем удалить заменённый remote object. Поздний ACK старого upload не может воскресить или вернуть предыдущую ревизию.

В нормальном устойчивом состоянии режима 3 — **один долговременный полноразмерный asset**. Временно допустимы две зашифрованные копии ради crash safety. Cleanup должен охватывать orphaned upload, thumbnail, preview, export, editor temp, удалённые и истёкшие файлы. Ошибка очистки не должна подменяться ложным статусом «удалено окончательно».

**OPEN вне TTL:** досрочное освобождение локальной уже синхронизированной копии и восстановление ключей на другом устройстве (ST-04); без выбранной recovery-стратегии нельзя удалять единственную **неистёкшую** копию. Для **истёкшего** снимка действует обязательное удаление даже если он не успел синхронизироваться, без повторной загрузки истёкших данных.

## 6. Миниатюры, TTL, автоматическая очистка и оставшиеся детали

**ST-05 — DECIDED.** Для каждого снимка максимум **одна отдельная миниатюра**, формат **WebP**, не больше **320 px по длинной стороне**, с сохранением пропорций. Шифровать до записи на диск и в S3. Отдельная миниатюра синхронизируется с S3 и может храниться на устройстве в **ограниченном, вытесняемом зашифрованном кэше**. Нет необходимости хранить её в кэше, если её можно получить из разрешённого S3; не создавать дополнительные размеры по умолчанию. ACL и TTL миниатюры не могут быть шире родительской фотографии.

**ST-06 — DECIDED.** **Нет отдельного постоянного preview** среднего размера. Для полного просмотра брать доступный разрешённый master, а для сетки — одну миниатюру. Если конкретная будущая функция требует отдельный экспорт, он должен иметь обоснование, owner, срок и права, и очищаться вместе со снимком.

**ST-09 — DECIDED в части срока и удаления.** Каждая фотография имеет ограниченный срок **не менее 24 часов и не более 45 дней**. В задании задаётся срок хранения, снимок получает неизменяемый для существующего снимка `expires_at` на момент съёмки. **Техническое умолчание до отдельного изменения владельцем:** время отсчитывается от `captured_at`, без задания срок **45 дней**, в новом задании начальное значение **45 дней**. Смена срока задания влияет на будущие снимки, не продлевая уже сделанные незаметно. Сохранение редакторской правки не обнуляет счётчик.

**Что удаляется при expiry:** encrypted original любого режима, compressed master, все edited versions, thumbnail, временные files, созданные share/export objects, облачные S3 objects, локальные blobs/кэш и **относящиеся к фото записи в локальной и серверной БД**, включая metadata, notes, cards и индексы/проекции. Связанные с несколькими фото объекты и сами Assignment/Team/Account удаляются **только если у них отдельное правило**, не каскадом одной фотографии. Каждый share/derived asset не может жить дольше `expires_at` родителя.

**Эффективный и экономный механизм:** Laravel Scheduler (запускается системным `cron` раз в минуту) делает **дешёвый запрос по индексу `expires_at`**, забирает небольшие пачки истёкших ID через cursor/seek (без сканирования всех фото), переводит их в `expired/deleting` и отправляет idempotent deletion jobs в очередь. Первая транзакция **сразу запрещает все чтения/скачивания/активацию ссылок**. Очередной worker удаляет физические S3 assets, thumb/share/versions, затем метаданные/Photo rows после подтверждения удаления, с retry/backoff и повторным подбором зависших job. При позднем upload/ACK tombstone/revision gate предотвращает воскрешение. После безопасной ликвидации остатков очищается и служебный tombstone; долговременной записи с личными metadata не остаётся. Не требуется таймер на каждый снимок или дорогой полный обход по расписанию.

**Локальные устройства:** клиент проверяет `expires_at` при открытии приложения, чтении/просмотре, resume и при каждом cleanup цикле; истёкший локальный снимок блокируется и его ciphertext/metadata/cache удаляются. Service Worker/background execution на iOS/Android нельзя гарантировать, когда PWA закрыта: сервер очистит S3/свою БД по расписанию, а офлайн-устройство очистит локальные данные при следующей возможности запуска. Проверка защищена от случайного показа истёкших материалов; offline clock tampering требует отдельного threat-model теста.

**Нюанс физического удаления:** если S3 поддерживает versioning, object lock, репликацию или резервные копии, необходимо отключить/настроить их так, чтобы они не сохраняли содержимое сверх разрешённой политики, иначе нельзя обещать физическое уничтожение ровно при expiry. При ошибке провайдера доступ закрывается немедленно, физическая очистка повторяется до подтверждения; лаг и failures наблюдаемы. Короткоживущая техническая запись удаления без фото/приватных метаданных может потребоваться до окончания retries, затем удаляется.
- **Editor history / Undo**: режимы 2 и 3 определяют сохранение исходника и текущей правки, но не утверждают историю всех редакторских версий; во время активного редактирования временные операции допустимы в памяти.
- **Photo Browser** — список/проекция фото в заданиях, не отдельные файловые копии каждого фото. URL коллекции сам по себе не даёт прав на фотографии.
- **Photo Card / share** — метаданные/ACL независимо от байтов; дополнительный flattened/privacy-masked export допускается только по отдельно утверждённой политике публикации и TTL.
- **Сжатие**: формат, размер, качество, предельные размеры, EXIF/GPS, метрики качества и производительности — OPEN. Сжатие не должно незаметно ухудшать фото сверх утверждённых параметров.
