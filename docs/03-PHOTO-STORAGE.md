# 03. Фото: размещение, версии, миниатюры, экономия и удаление

**Статус: OPEN — обсуждение с владельцем.**  
**Никакая топология S3/local/browser и никакая политика удаления ещё не утверждена.** Это журнал требований и решений, а не спецификация, готовая к реализации.

## 1. Подтверждённые требования владельца

1. Места для фотографий **очень мало**. Не плодить redundant originals, previews, thumbnails, editor versions, ZIP, imports, abandoned uploads.
2. **Оригинал сохраняется отдельно только если задание прямо требует его сохранения.**
3. В остальных случаях **оригинал должен заменяться**, а не копиться рядом с результатом; нужно уточнить, какое действие и момент замены имеются в виду.
4. Ненужные объекты должны удаляться, а ещё лучше — вообще не материализовываться без необходимости.
5. Фотографии, задания, Photo Browser, редактор и Photo Card должны работать устойчиво, в том числе при повторном открытии и без сети в пределах разрешённого локального доступа.
6. Хранение и доступы не должны зависеть от мессенджера.

### ВАЖНО: конфликт со старым контрактом

В `1troitsky/photobunker` исходная модель хранит encrypted original, preview, thumbnail и версии как независимые объекты, а оригинал обычно immutable. Перенос этой структуры **как обязательной** прямо противоречил бы новой политике минимизации байтов. При переносе проверенных server/crypto контрактов нужно явно изменить модель и миграции, не ломая уже существующие фото.

## 2. Три разных значения слова «локально»

| Место | Что означает | Ограничение |
| --- | --- | --- |
| **На устройстве пользователя** | Фото внутри разрешённого browser/PWA-хранилища (кандидаты: OPFS, IndexedDB), доступно без сети | Хранилище браузера ограничено и иногда может быть очищено системой; это не надёжная единственная резервная копия |
| **S3 у нас на сервере** | Например, self-hosted Garage/MinIO, данные в volume/дисках нашего сервера | Это **серверное**, а не offline-хранилище телефона; если сервер и storage на одном диске, это не backup |
| **S3 у внешнего провайдера** | Объектное хранилище S3-compatible в дата-центре провайдера | Требуются сеть, платёж/лимиты, политика хранения и защиты; не заменяет локальный offline-cache |

Существующий PhotoBunker использует Garage как private S3-compatible storage в Docker Compose **и** локальное browser-хранилище. Сам факт его существования **не означает**, что новая версия обязана использовать ту же конфигурацию или иметь по три копии каждого снимка.

## 3. Рекомендуемая для обсуждения модель «минимум файлов» — НЕ УТВЕРЖДЕНА

Кандидат: на каждый снимок — **один текущий рабочий master** полной нужной размерности и отдельный исходный original только когда сохранение оригинала предписано зафиксированной политикой задания. Это логическое правило, не указание всегда хранить два файла или обязательно загружать их в S3.

| Сущность / файлы | Когда нужны | Кандидат на жизненный цикл |
| --- | --- | --- |
| **Current master** | Один материал, который пользователь открывает/редактирует/смотрит | Один актуальный; новая обработка замещает прежний после безопасного commit |
| **Preserved original** | **Только** когда задание явно требует сохранить исходный снимок | Отдельный защищённый immutable объект с TTL/права задания; без требования не удерживается |
| **Thumbnail** | Для быстрой галереи/браузера; может требовать особого ограниченного разрешения | Маленькая производная в ограниченном кэше либо разрешённый маленький remote asset, **не создавать по умолчанию несколько размеров** |
| **Preview** | Только когда для скорости/full resolution/ACL он реально нужен | Если достаточно master или thumbnail, не заводить отдельный бессрочный preview |
| **Editor temporary** | Во время операции и безопасной замены | Краткоживущий, автоматически убрать после commit/rollback |
| **Editor history/version** | Только если политика требует историю/undo после закрытия | **OPEN:** нужна ли постоянная история? Не копировать каждый полный bitmap без решения |
| **Photo Card** | Отдельный набор метаданных и ссылок | Карточка ссылается на разрешённый rendition; не дублирует master автоматически |
| **Публикация / share-export** | Если необходимо выдать независимое, например flattened/privacy-masked представление | Отдельный объект только при публикации, с TTL и revoke; не даёт права на original |
| **Photo Browser** | Авторизованный список ссылок на фото из заданий | Индекс/проекция, **не копирует файлы** в каждую подборку |

Это лишь **предложение**, требующее уточнения UX и прав; например, thumbnail-only доступ участника может требовать отдельной маленькой зашифрованной производной, даже если фотография хранится в единственном master.

## 4. Что может означать «перезапись оригинала»

**Предлагаемая семантика (требует подтверждения):**

- При съёмке создаём один рабочий снимок. Если задание установило `preserveOriginal=true`, его исходные пиксели остаются отдельным зашифрованным original.
- Если **нет** такого требования, после применения правки новый **current master** становится единственным долгоживущим полноразмерным изображением; предыдущее содержимое удаляется. Пользователь сознательно теряет возможность восстановить прежние пиксели после окончательной фиксации правки.
- **Нельзя** перезаписывать единственную зашифрованную копию на месте, если сбой питания/вкладки/квоты оставит битый файл. Минимально надёжный сценарий — создать временный новый зашифрованный asset → проверить запись → атомарно переключить ссылку на master → удалить старый. Пиковое кратковременное потребление может включать две копии; постоянное — одну. Удаление старого после краша подбирается reconciliation/cleanup.
- Версии в редакторе и временные undo не должны тихо превращаться в вечный архив полных JPEG/PNG.

**OPEN:** пользователь подразумевает именно замену при сохранении правки или иную замену/сжатие сразу после съёмки? Этот вопрос меняет контракт editor и storage.

## 5. Thumbnail и preview — неизбежный компромисс

- «Никогда не создавать миниатюры» может сделать сетевую галерею слишком дорогой: для 100 превью пришлось бы загружать 100 полноразмерных файлов. Крошечный thumbnails cache обычно экономит **трафик и RAM**, но потребляет немного дискового пространства.
- «Всегда сохранять 80px + средний preview + full image в S3» может растратить дефицитный storage. Для thumbnail-only доступа может хватить **одного отдельного маленького разрешённого asset**.
- Возможный подход: ограниченный local cache (LRU + budget + TTL) для экранов; лишь необходимые remote renditions; никакого дублирования в подборках.
- Кэш можно очищать автоматически, **но не** терять единственный current master и не удалять данные, которые ещё не были надёжно синхронизированы/сохранены.
- Локальный кэш нельзя выдавать за право доступа после онлайн-отзыва: при возвращении сети перепроверять права до загрузки новых закрытых материалов.

## 6. Как не оставлять мусор

Будущая реализация должна иметь **единую учётную модель asset lifecycle**: owner/account, photoId, purpose (master/original/thumb/export/temp), storage tier, size, revision, TTL, access scope, state, deletion job id. Это **концептуальные поля**, не утверждённая схема базы.

Процессы:
1. Не материализовывать дополнительные копии без явного потребителя и политики.
2. Резервировать место и проверять квоту **до** тяжёлой обработки; при ошибке сохранять доступ к прежней корректной версии.
3. Использовать crash-safe commit: физическая запись → проверка → commit указателя/manifest → удаление заменённого asset.
4. Retrying cleanup для неполных upload, старых editor temps, expired shares, tombstones, failed imports и потерянных временных файлов, включая restart.
5. Не удалять единственную unsynced фотографию и не считать очистку S3 оконченной до проверки физического удаления (в некоторых хранилищах удаление отложено).
6. Account/device scope и TTL распространяются на thumbs, caches, exports и временные производные; но нельзя смешивать cache eviction и разрушительное удаление фото.
7. Ограничить бюджеты **отдельно** для устройства/remote, включая temporary peak; при дефиците места честно останавливать операцию без повреждения прежних данных.

**Нулевая временная аллокация не гарантируется** для надёжной атомарной замены и криптографии. Цель — **никаких лишних долговременных дубликатов и гарантированная уборка** после прерываний.
