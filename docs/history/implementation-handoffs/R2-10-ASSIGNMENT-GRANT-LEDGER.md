# R2-10 explicit Assignment invitation ledger — NOT photo access

Signed, atomic operations live at `assignments/v1/grants/operations/{opId}`; server stores only invitation ciphertext, code hash, opaque assignment/recipient IDs, role, generation and lifecycle. Invites require a real owner, an accepted contact, neither party blocked, ready recipient account, and ≤7-day invitation expiry. Only target accepts/declines/leaves; owner revokes. All operations use exact canonical JSON, device signatures, idempotent operation IDs, immutable grant identity and generation CAS. Snapshot only returns invitations for the current account, and only its encrypted invitation payload.

**This does not confer PhotoSync object/manifests/review/read permission.** Existing owner-only photo controller remains unchanged. Accepting an invitation does not prove the user knows the out-of-band code or has decrypted the invitation; the client must verify the code/secret locally *before* sending acceptance. This is not implemented yet. The code must never be sent to server or placed in URL. The table is a preliminary authorization ledger; future read policy must check accepted role, generation, current blocks/contact, assignment state, asset scope, photo TTL and signed envelopes on **every** entrypoint. A revoked invitation cannot reactivate; existing offline content cannot be erased remotely.
