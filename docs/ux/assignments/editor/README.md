# Assignment editor — Fieldwork / UX prototype

**Состояние:** дизайн подтверждён владельцем в чате 2026-11-07. Это **эталон frontend**, а не исправление production UI. Продакшен: `compat/assignment-release/apps/web/src/views/AssignmentEditView.vue`. Конкретное UX-решение — сохранить прежнюю полезную структуру редактора и унифицировать правила, прежде всего Public Card.

## Открыть

Из корня проекта: `python3 -m http.server 8080`, затем `http://localhost:8080/docs/ux/assignments/editor/`.

- [`index.html`](index.html) — структура экрана со всеми четырьмя вкладками.
- [`style.css`](style.css) — стили редактора; наследует `../style.css` от утверждённого списка заданий, поэтому размеры Header / Content / preview device и палитра общие.
- [`app.js`](app.js) — **локальный интерактивный демо-код** без API, пользователей и сохранения. Работают вкладки, раскрытие зависимых правил, выбор пресета/команды, редактирование участников, проверка формы, reset, статусный диалог, переключатель Mobile/Desktop.
- Вернуться к [списку заданий](../index.html).

## Утверждённая геометрия

- Тёмный Fieldwork/Spotify-inspired стиль, дозированный зелёный акцент, небольшие радиусы, высокая читаемость.
- Header: кнопка «Назад», `[pb] PhotoBunker` и системный статус под названием. Ниже: «Новое задание» и четыре вкладки.
- Контент прокручивается независимо от шапки. На Desktop блоки редактора могут располагаться в 2 колонки.
- Снизу в эталоне **постоянная кнопка «Создать задание»**, справа; слева статус локального черновика/сброс демо. Это отдельное **предложение, принятое для прототипа**. Production сейчас использует debounce-автосохранение. Перед внедрением нужно решить явное создание vs autosave, не смешивать две модели и не терять несохранённые данные.

## Вкладки / согласованное содержимое

| Вкладка | Поля |
| --- | --- |
| **Основное** | Название (до 80), инструкции (до 4000), дата и время начала, необязательная дата окончания с условным раскрытием |
| **Камера** | Пресет камеры и создание нового, целевое количество снимков (1–9999), список обязательных кадров построчно |
| **Участники** | Владелец «Вы», команда и её выбор, участники с ролями `curator/contributor/viewer` и photo scope `default/none/thumbnails/all`, добавление из контактов |
| **Правила** | Нумерация, категория и допустимые категории, описание/мин. длина, правки/оригинал/удаление, галерея/миниатюры, передача/ограничение участниками, **Public Card в самом конце** |

### Public Card — обязательная договорённость

В нынешнем `AssignmentEditView.vue` компонент `PublicCardSettings` стоит **первым** внутри вкладки «Правила» и визуально не совпадает с соседними блоками. В макете он перемещён **после «Передача фотографий»** и имеет **точно такой же блок, разделители, переключатели, зависимое раскрытие**.

Поля из реального `PublicCardPolicy` сохранены без изменений: `enabled`, `contributor`, `capturedAt`, `editedAt`, `location`, `description`, `tags`, `metadata`. Дефолты из `studio/public-card-policy.ts`: `enabled=true`, `location=true`, `description=true`, остальные `false`. Public Card политика влияет только на новые фото задания, не меняет уже сделанные и **сама по себе не создаёт публичную ссылку**. Настройки карточки **не должны повышать разрешения на чтение, передачу, скачивание или отменять ACL/TTL**. Переносить реальную политику из существующего компонента, не писать новый backend.

## Важные факты и ограничения при внедрении

1. **Это не полноценный заменитель `AssignmentEditView.vue`.** Сохранение, права, модель `Task`, команды и приглашения уже реализованы в production, а здесь только пример UX.
2. Код в прототипе содержит **демонстрационные имена, команды и пресеты**. Никаких реальных пользовательских данных и приватных фото. Демоданные меняются только в памяти открытой страницы и теряются после reload.
3. Изменения в форме не уходят на сервер. Кнопка «Создать задание» валидирует пример и показывает честное подтверждение *демонстрации*, а не успех API.
4. `Task.targetCount` сейчас **обязательный integer 1–9999**, хотя `ts_and_ux.md` описывает целевое количество как опциональное. В макете оставлено значение 30 и поведение текущего валидатора. Это отдельный продуктовый/модельный вопрос, не решать молча через UI.
5. В настоящем редакторе уже есть автообновление, revision/conflict handling и переход к редактору пресетов. При внедрении **сохранить всё это** или явно согласовать изменение сохранения; недопустимо повторять простую `newTask` или демо-копирование вместо доменных операций.
6. Для участия и команды использовать действующие `ParticipantsEditor` и `TeamPicker` и их проверки разрешений. Любая новая иконка задания из списка — отдельный будущий атрибут модели, здесь намеренно не добавлен.
7. Никаких изменений `main`, фактических систем шифрования, PIN, TTL, GPS, cloud sync или production UI в этом PR.

## Приёмка будущей production-реализации

Показывать изменённый реальный `/assignments/new` на телефоне и Desktop; проверять четыре вкладки, скролл, keyboard/safe area, условные поля, команду/участников, Public Card в конце вкладки «Правила», сохранение и возврат назад. Передачу полей между вкладками и существующую валидацию не терять. Только явное принятие владельцем позволяет считать экран **ACCEPTED**.
