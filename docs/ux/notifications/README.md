## Страница «Уведомления»

1. Утверждён **общий Fieldwork Shell:** Header 64 px и Dock 82 px, нейтральный тёмно-серый фон, зелёный акцент, умеренные скругления, без отдельной синей темы и круглых action buttons.
2. На **самой странице уведомлений** в Header находятся **две иконки:** «Прочитать все» и «Настройки уведомлений»; это не текстовые кнопки в теле страницы. **Кнопка тарифа здесь скрыта**. Отдельная кнопка/строка «Назад» над заголовком **отсутствует**.
3. Ниже Header: заголовок **«Уведомления»**, затем близко расположенное горизонтальное меню **«Все» / «Непрочитанные»**. Не добавлять счётчик «Непрочитанных: N» в заголовок.
4. Непрочитанное событие отмечено **зелёной точкой у верхнего левого угла иконки слева**. Прочитанные события заметно, но умеренно тусклее. Кнопка «Прочитать все» меняет состояние всех событий.
5. **Листается единая основная область страницы** с обычным прокручиванием; не создавать вложенный scroll container для списка уведомлений. Header/dock остаются стандартными, заголовок и вкладки сохраняют структуру при просмотре.
6. **Открытие уведомления — раскрытие на том же экране:** остальные уведомления скрываются, выбранное разворачивается; Header, заголовок и горизонтальное меню остаются без смены страницы.
7. Развёрнутое событие состоит из **одного элемента с тремя частями:** шапка (иконка, заголовок, подзаголовок, время/дата), контент (без повторного вложенного «блока в блоке») и футер **«К списку уведомлений»**. Футер возвращает список без лишних маршрутов.
8. Уведомление является **точкой действия**: приглашение в команду даёт «Принять» / «Отклонить»; напоминание о задании, файле, новых материалах и бэкапе показывает контекст соответствующего объекта и действия. **В текущем HTML это локальные демо-объекты**, реальные deep links/ACL/серверные операции будут внедряться отдельно. При переносе в приложение событие должно иметь стабильный тип, ID цели, допустимое действие и корректную авторизацию.
9. Колокольчик со счётчиком новых событий предусмотрен в Header других соответствующих экранов Settings (не обязателен везде); он открывает полноценную страницу, **не popover/дропдаун**. На странице уведомлений вместо тарифной кнопки расположены контекстные действия.

## Страница «Настройки уведомлений»

- Категории: приглашения в задания/команды, изменения заданий, приближение срока задания, новые файлы, проверка материалов, скорое удаление файлов, резервные копии, подписка, события безопасности.
- Подписи краткие и пользовательские: **без слова «Например,»** и без технических пояснений про вычисления сервером; время напоминаний описывается конкретно (например, за 24 часа до конца задания или TTL файла).
- Отдельные параметры: проверка доступности доставки (внутренние события / системные push / разрешение устройства), счётчик на иконке приложения **где поддерживается**, тихие часы с началом/окончанием.
- **«Отмена» и «Сохранить»** закреплены в панели над Dock на странице настроек; отмена возвращает сохранённое состояние, сохранение меняет демо-состояние. В списке входящих этой панели нет.
- Из Settings поиск с RU/EN ключевыми словами открывает **конкретную настройку**, а не только корень страницы. Сохранять ранее утверждённую модель глобального поиска из [App Appearance 1.2](../app-appearance/README.md).
- Не показывать пользователю технические сообщения вроде «Демонстрационные события», «Badging API обнаружен», категоричную тревожную шапку «Уведомления заблокированы». Отображать понятное, фактическое состояние и способы включения без ложных гарантий.

## PWA/OS ограничения — обязательные для реализации

- **Внутренний список событий** и их прочтение — функции приложения; они **не зависят от разрешения системных push** и не должны пропадать при отказе в разрешении. Серверная/Local-First синхронизация реальных событий — **отдельная реализация**.
- Системные push требуют действующей реализации через Service Worker, Push API/подписку пользователя, HTTPS/поддерживаемый контекст, сервер отправки, правильные ОС/браузерные разрешения. В частности, Web Push на iOS имеет условия установки PWA на домашний экран и поддержки соответствующей версии iOS. Нельзя обещать доставку или произвольное управление звуком, вибрацией и локскрином независимо от ОС.
- `Badging API`/значок приложения поддерживается не на всех платформах, и системное отображение может отличаться. Счётчик внутри приложения всегда доступен как UI.
- Напоминания со сроками должны опираться на проверенные серверные TTL/дедлайны и не зависеть от гарантированного фонового исполнения PWA. Права доступа, открытие адресатов, сноска на объект и дедупликация событий требуют серверного контракта.
- **Не допускать утечек приватных данных в push:** безопасный минимальный текст по умолчанию, защищённый переход и повторная проверка доступа после открытия приложения. Уведомления об Emergency PIN и рисках безопасности не должны раскрывать секретный сценарий.
- HTML использует **только вымышленные события и локальный интерактивный state**. Реальных push, отправки приглашений, изменения ролей, бэкапов или TTL/GC в нём нет. Существующий production Service Worker сам по себе не доказывает поддержку push.

**Проверка фиксации:** автономный HTML текстово в точности восстанавливается из index + CSS + JS; синтаксис JS проверен через `node --check`. Владелец утвердил UX 1.5; production push, browser-device E2E и реальная интеграция **NOT TESTED / NOT IMPLEMENTED**. `main` и production-код не изменялись.
