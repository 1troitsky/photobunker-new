# 02. Архитектура PhotoBunker: границы и устойчивость

**Статус: APPROVED ARCHITECTURAL INVARIANTS (2026-10-28).** Разработка разрешается по назначенным Codex `Ready` Issues и правилам [COLLABORATION](../COLLABORATION.md). Это **проектные обязательные границы**, а не утверждение, что соответствующий код уже готов. Открыты только конкретные технические выборы, явно помеченные OPEN в профильных контрактах. Владелец утверждает изменения продукта, Codex организует setup/проверки, ChatGPT исполняет большую часть Issues.

## 1. Цель архитектуры

Система, которую **трудно сломать случайным изменением и легко локально исправить**, а не просто «чистый код». Изменение камеры, правил хранения оригинала, редактора, заданий или Photo Card не должно требовать синхронного переписывания других функций.

### Обязательные свойства будущего решения

- **Локальная реакция.** Маршрутизация, shell, cached-данные и действия, возможные офлайн, не ждут сети. Клиент не обещает доступ к материалу, не прошедшему нужную локальную авторизацию и разблокировку.
- **Разделение полномочий.** UI не проверяет безопасность самостоятельно. Сервер независимо проверяет ACL/TTL, клиент отдельно применяет локальные/криптографические ограничения.
- **Стабильные контракты.** Внешние DTO валидацией отделены от domain-моделей; изменение сервера локализовано в адаптере.
- **Отказоустойчивость.** Неудача сети, заполнение хранилища, обрыв обновления, отзыв доступа, перезапуск приложения, гонка запросов — нормальные явно смоделированные состояния.
- **Confidential capture.** Никакой локальной plaintext persistence или сохранения фото в системной галерее. Изображение и чувствительные метаданные шифруются до локальной записи; метаданные фиксируются отдельно в локальной БД вместе с photoId, затем синхронизируются с серверной БД.
- **Минимизация байтов.** Вопрос «что физически сохраняем и как это удаляется» не может решаться произвольно внутри компонентов UI. Режим retention закреплён в политике задания: неизменённый оригинал без дополнительного сжатия (UI пока disabled), сжатый оригинал отдельно от edit или сжатый master с заменой edit (default).
- **Тестируемые границы.** Запрет архитектурных зависимостей и CI/test gates необходимы, иначе это просто очередной документ обещаний.

## 2. Отдельные функциональные модули

| Модуль | Единственная область ответственности | Чего он не делает |
| --- | --- | --- |
| Capture | Камера, разрешения, съёмка, метаданные момента захвата, пресеты | Не решает, сколько оригиналов хранить; не загружает напрямую на сервер |
| Photo Library | Каноническая модель фото, локальный commit, жизненный цикл asset, галерея, доступы к данным фото | Не содержит UI редактора, задания или Card-публикацию |
| Assignments | Конфигурация задания, роли, участники, разрешения и требования к фото, в том числе сохранение original | Не хранит байты фото и не реализует редактор |
| Photo Browser | Авторизованная проекция по выбранным заданиям, фильтры, доступ к разрешённым фото | Не дублирует изображения и не расширяет права одной лишь ссылкой на коллекцию |
| Editor | Операции над фото, вычисление нового изображения и результат редактирования | Не меняет файлы напрямую, не владеет originals или server upload |
| Photo Card | Отдельная карточка, разрешённые поля, правила доступа к представлению/экспорту, share/TTL | Не эквивалентна исходному фото; не выдаёт original автоматически |
| Identity & Access | Стабильные User/Account IDs, вход, first trusted device, recovery, session/device capabilities и права | **Центральная identity**, но без гигантской User-модели; PIN не является ключом и никакой модуль не зависит от будущего Messenger/Billing |

**Мессенджера в этом составе нет.** Нет скрытой обязательной зависимости заданий от Matrix.
### Независимая идентичность для будущих модулей

**User/Account ID — главный постоянный идентификатор пользователя, но не монолит бизнес-логики.** Модули фото, заданий и команд используют только стабильный `user_id`, Identity/Authorization API и разрешённые capabilities. В будущем Billing/Subscription (плательщик User или Team) и Messenger подключаются как независимые bounded contexts с собственными данными и public ports; их SDK/таблицы/события **не** нужны в core boot в первой версии. Не строить под подписки или Messenger универсальный фреймворк заранее. Полный контракт в [11 — Identity and Keys](11-IDENTITY-AND-KEYS.md).


## 3. Утверждённые границы зависимостей

Каждый модуль имеет `domain`, `application`, `infrastructure`, `ui`, и **публичный контракт** для остальных модулей.

- `domain`: чистые сущности, значения, инварианты, правила; без Vue, HTTP, браузерных API.
- `application`: небольшие use-cases (`capturePhoto`, `saveEdit`, `createAssignment`, `revokeCard`) и объявленные порты к данным/устройствам.
- `infrastructure`: реализации портов: Laravel API, browser storage, crypto, native/browser camera, remote object store.
- `ui`: presentation state и компоненты; без импортов сетевых SDK, raw IndexedDB, S3, криптографических примитивов.

**Межмодульный доступ только через публичный API**, без импорта внутренних файликов другого feature. Нет циклов; нет общего гигантского store как источника истины всей системы.

Пример однонаправленного взаимодействия:

```text
Camera UI
  -> Capture use-case
  -> Photo Library application port: commitCapture(capture, policy)
  -> EncryptedBlobStore: OPFS ciphertext с IndexedDB Blob fallback + Dexie metadata/journal/outbox
  -> Photo Library updates its canonical state
  -> Gallery/Editor/Photo Card consume only published Photo Library API
```

Assignments предоставляет неизменяемый снимок `CapturePolicy` со связанным идентификатором и ревизией задания, но **не пишет** в файл снимка. Photo Library не вынуждена знать Vue-структуру задания.

## 4. Источник истины, операции и инварианты

Потребуются типизированные модель `Photo`, `PhotoAsset`, `CapturePolicy`, `Assignment`, `PhotoCollection`, `Card`, `EditResult`, `PinPolicy`, но их **физические схемы ещё не утверждены**.

Для каждой операции нужны ответы на вопросы:
1. Что появляется в UI до сети и что значит «сохранено»?
2. Как локально надёжно фиксируются разрешённые данные?
3. Какой идентификатор обеспечивает идемпотентность, если ответ потерян?
4. Где проверяются версия, существование, TTL и ACL?
5. Что делает отзыв доступа, смена аккаунта, offline/reload?
6. Какие **физические** assets создаются/переписываются/удаляются, когда возникают временные копии, кто убирает сирот?
7. Что делать при storage full, kill mid-write, quota и ошибке удалённого подтверждения?

Локальная фиксация и серверный ACK — разные состояния. Не рисовать «сохранено в облаке» по факту только локального commit. Удаление логически закрывает доступ до фонового физического cleanup; при ошибке сохраняется задача повторного удаления. Поздний upload/ACK никогда не воскрешает tombstone.

## 5. Storage Lifecycle — отдельный центральный контракт

**Не** разносить политику по CameraView, GalleryView и EditorView. Будущий `PhotoStoragePolicy` должен определять набор сохраняемых файлов и срок жизни каждого на основе утверждённых владельцем правил.

Особенно важно: старое требование «оригинал всегда immutable и хранится навсегда до TTL» **не переносится как универсальное правило**. Утверждены **три режима** [ST-02/ST-03](03-PHOTO-STORAGE.md): (1) исходный файл без повторной компрессии — интерфейсный выбор выключен; (2) сжатый оригинал с отдельным edit; (3) сжатый master, который заменяется edit — default. Правило фиксируется при съёмке. Безопасная замена означает новую временную зашифрованную запись, подтверждение и переключение указателя перед очисткой прежней, **не рискованную in-place перезапись**. Только один модуль хранения управляет этим жизненным циклом.

Канонический PhotoAsset-owner учитывает remote/local usage и каждый derivative по owner/purpose/expiry/delete state. **У каждой фотографии expires_at 24ч–45д; thumbnail/версия/share/metadata не живут дольше неё.** После expiry сервер немедленно запрещает чтение и через indexed scheduler + batch deletion queue удаляет S3 assets, originals/edits/thumbs и DB records; клиент чистит локальную копию при следующем запуске. Отдельных постоянных previews нет.

## 6. Технический baseline и отложенные интеграции

- **Сервер:** Laravel + PostgreSQL и очереди — рабочая целевая архитектура; **интеграция PostgreSQL/Garage не входит в R2-01** и выполняется по соответствующим backend/storage Issues. Конкретную версию Laravel Codex проверяет при установке, не копирует старую схему БД автоматически.
- **Клиент:** Vue 3 / TypeScript PWA; **Dexie/IndexedDB** для локальных metadata/journal/outbox, **OPFS только для encrypted blobs** при поддержке, **encrypted IndexedDB Blob fallback**, **Pinia только для ephemeral UI state**. Проверка Safari/iOS, storage.persist()/quota/eviction — обязательна в R2-04. Vue Router/инструмент интеграции выбирается Codex без нарушения немедленной навигации и доступа к локальным данным. См. [12](12-CLIENT-STORAGE-AND-TRUSTED-TIME.md).
- **Хранилище файлов:** утверждён гибрид **local encrypted → S3**, первый совместимый backend — **Garage**. ST-02/03 — три режима originals; ST-05/06 — единственная encrypted WebP thumbnail ≤320px, отдельного постоянного preview нет; ST-09 — **TTL 24 часа — 45 дней** по заданию и автоматическое удаление всех photo-related files/DB metadata; ST-12/13 — раздельная metadata DB, encryption before persistence, запрет системной галереи. Конкретные SDK/локальный адаптер, качество сжатия и история редактора уточняются Codex по соответствующему Issue.
- **Crypto/Identity:** утверждённые жизненные состояния first-device bootstrap и recovery envelope — в [11](11-IDENTITY-AND-KEYS.md), trusted-time policy в [12](12-CLIENT-STORAGE-AND-TRUSTED-TIME.md). Использовать проверенные примитивы/тест-векторы, делать независимый threat review в Codex, не придумывать свою AEAD.

## 7. Машинные ограничения будущего репозитория

При старте реализации выбранной Codex Ready Issue:
- проверка запретных импортов и dependency cycles; негативные тесты должны доказать, что нарушающий build падает;
- typecheck, unit tests для чистого domain, contract tests для адаптеров;
- тесты storage/rollback/recovery и удалений (storage full, offline, restart, ACK after revoke);
- production build + browser/mobile E2E для **полного пользовательского сценария**, без подмены dev режимом;
- проверка выпуска без Matrix зависимостей и без legacy plaintext prototype;
- отдельные проверяемые критерии размера и сложности файлов; они вспомогательны, главное — **разрешённые связи**.

**Нельзя утверждать, что это уже реализовано.** Этот раздел — требования к будущему процессу и архитектуре.

## 8. Управление решениями

- Все неутверждённые вопросы отмечаются **OPEN** в существующих документах.
- После согласования с владельцем записываются: решение, причины, последствия, исключения, критерии проверки и дата. Изменение не теряет контекст.
- Бэклог roadmap уже создан. Новые Issues только по согласованному изменению scope, не создавать параллельную очередь.
- **Roadmap уже опубликован** в [08](08-ROADMAP.md); Codex выстраивает очередность, настраивает окружение и выдаёт ChatGPT задачи. Прежнего запрета на начало проекта нет; Ready/dependency/review gates действуют.
