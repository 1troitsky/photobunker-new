# 14. Independent Implementation Pipeline & Replaceable UI — OWNER APPROVED

**Решение владельца: 2026-10-29.** Этот документ нормативен для **процесса реализации оставшихся Issues** и границ UI/UX. Он дополняет [AGENTS](../AGENTS.md), [CHATBOT-AGENTS](../CHATBOT-AGENTS.md), [COLLABORATION](../COLLABORATION.md), [02 Architecture](02-ARCHITECTURE.md), [06 UX/UI](06-UX-UI.md), [07 Quality](07-QUALITY-AND-RELEASE.md) и [08 Roadmap](08-ROADMAP.md). Если прежний процесс требует назначения Ready от Codex, предварительного merge зависимости или остановки *разработки* на UX-review, **для текущей фазы исполнения применяются правила ниже**. Security, recovery, storage, ACL, TTL и нормативный product baseline этим решением не ослабляются.

## 1. Разделение фаз и полномочий

**Фаза I — Independent Implementation.** ChatGPT выполняет оставшиеся согласованные Roadmap Issues последовательно, **без ожидания Code Review/тестирования/merge/назначения от Codex**. Владелец указывает первую или следующую Issue; дальнейшую согласованную последовательность можно брать по Roadmap без нового разрешения Codex. На каждый Issue: независимый scope, одна рабочая ветка, **один Draft PR**, честные проверки/NOT RUN и передача ссылки в общий список. Отсутствие локального рабочего окружения не даёт права заявлять, что тесты прошли. В Phase I **ни один функциональный PR не сливается в main** и не помечается Verified/Integrated/Accepted только за наличие кода.

**Исключение для запуска нового процесса:** этот документационный PR после review Codex интегрирует в `main` по прямому поручению владельца; это **не** старт финальной интеграции функциональных Issues. После этого Codex не нужен для передачи очередной Issue. Codex может независимо подготовить окружение и заранее давать замечания, но **его доступность не блокирует реализацию**.

**Фаза II — Integration & Verification (Codex).** После завершения Implementation очередь PR замораживается для новых функций. Codex на фактическом окружении проверяет **всю цепочку**, устанавливает dependencies, исправляет проблемы **в соответствующих ветках/PR**, повторяет полный набор тестов, интегрирует в `main` в порядке зависимостей, проверяет сквозные сценарии на объединённом состоянии. Никакие исправления не теряются в нижележащих ветках. Нельзя объявлять production-ready перед security review, fault injection, staging+HTTPS E2E, реальными iOS/Android проверками и принятием владельца. Владелец утверждает продуктовые решения, UX и выпуск; Codex руководит интеграцией, но не является условием начала написания кода.

**Критические stop-условия** (ошибка шифрования, plaintext persistence, потеря несинхронизированных фото, обход ACL/TTL, unsafe destructive PIN/migration и т. п.) остаются: не применять опасный обход, явно зафиксировать defect/STOP и ограничить затронутую функцию до безопасного исправления. Допустима работа над другими независимыми Issues; STOP **никогда** не превращается в выдуманный PASS.

## 2. Dependencies: не ждать merge, но не игнорировать код

Roadmap [08](08-ROADMAP.md) — единственный список задач и логических зависимостей. **Независимость от Codex не означает независимость задач друг от друга**. Перед Issue составить список точных upstream contracts/веток/SHA, убедиться, что требуемая реализация доступна хотя бы в незалитой ветке; не писать функцию, полагаясь на несуществующий модуль.

**Правило по умолчанию — serial integration spine (stacked PRs).**

1. Для первой незалитой Issue выбрать последний фактический upstream commit, уже содержащий необходимые функции (например, head R2-08 для R2-09). Зафиксировать одновременно свежий `origin/main` и выбранный `base SHA`; если upstream не интегрирован, **не** начинать с `main` и не дублировать код. Прежде чем менять ветку, проверить, не существует ли она уже.
2. Создать `chatbot/r2-XX-<slug>` **от конкретного зафиксированного SHA upstream head**; не force-push и не менять `main`. Создать **один Draft PR** с `Closes #N`, где `base` = **имя предыдущей upstream-ветки**, а `head` = текущая ветка. Так diff данного PR содержит только собственный Issue.
3. Следующую Issue создавать от предыдущего результата **в порядке топологической сортировки графа**. Если функция зависит от нескольких веток, предпочитать spine, уже содержащий их коды. При необходимости собрать отдельную integration ветку из известных SHA через обычный merge, документировать ancestry и конфликты; не cherry-pick вслепую, не создавать второй PR для того же Issue, не превращать cross-issue merge в скрытый продуктовый scope.
4. **Одна Issue — один Draft PR**; функция должна быть полностью реализована в своей ветке с тестовыми сценариями/контрактами даже если окружение для запуска отсутствует. Находка ошибки в upstream: исправить upstream PR и перенести исправление в последующие ветки **обычным merge-коммитом без переписывания опубликованной истории**; повторно проверить контракт. Изменения downstream не обязаны быть линейно cherry-picked в `main`.
5. Каждый PR документирует `main SHA` на дату старта, фактический `base branch + SHA`, `merge-base`, `head SHA`, список upstream PRs, новых контрактов, собственный diff `base...HEAD`, риски, честный PASS/FAIL/NOT RUN и инструкции интеграции. **Не писать “main...HEAD” как единственный scope diff для stacked PR**: он включает чужие незалитые Issues.
6. Если `main` изменился извне: сравнить фактическую историю, не reset/force-push, не перебазировать вслепую; план синхронизации — явный и проверяемый. Незавершённый review upstream сам по себе не блокирует следующий Issue, но несовместимый API/contract должен быть исправлен до downstream реализации.

**Финальное слияние:** Codex идёт снизу вверх по dependency order. Перед каждым merge проверяет `head/base/merge-base`, применяет исправления, обновляет base следующих PR до нового `main`/доказанно интегрированного parent, повторно смотрит scope diff и CI. После последнего merge выполняет **полную** end-to-end verification объединённого приложения и фиксирует результат. Наличие зелёных тестов отдельных PR не доказывает общую корректность.

## 3. Самостоятельная подготовка Issues (без Codex)

- Статусы GitHub Project `Backlog/Ready/Blocked` **не являются техническим разрешением или запретом Phase I**: реальная `Implementation Ready` определяется наличием согласованного scope, необходимых upstream контрактов, безопасности и отсутствием принципиально OPEN owner decision.
- ChatGPT читает **свежие** `AGENTS.md`, `CHATBOT-AGENTS.md`, `COLLABORATION.md`, Roadmap, нормативные документы, полный текущий Issue и GitHub SHA upstream; не полагается на прошлую память или устаревший статус Project.
- Перед написанием кода собирает `Legacy evidence` с **точными путями** из `1troitsky/photobunker` (read-only GitHub), `REUSE / ADAPT / REFERENCE / REJECT`, test vectors, опасные части. Если Issue уже имеет список, открыть **каждый** путь. Если список отсутствует — самостоятельно сделать узкий legacy-check, внести evidence в **существующую Issue** и только после этого кодить. Отсутствие evidence больше **не требует ждать Codex**. Не писать/форматировать старый repo и `_old`, не копировать legacy массово.
- Не создавать новые Issues или изменять продуктовые инварианты без владельца. Технические решения допустимы в пределах нормативных контрактов; значимое OPEN owner decision сообщить владельцу и сделать остальные безопасные/независимые части, **не выдумывать разрешение**.
- Для каждой задачи подготовить проверки и указывать реальные команды/результаты. Проверять доступными инструментами. **NOT RUN ≠ PASS**; не обещать, что “Codex всё исправит” вместо осмысленной архитектуры и проверяемого кода.

## 4. Replaceable UI/UX — жёсткая граница

**Цель:** владелец вправе заменить весь внешний вид, навигацию, расположение рабочих областей, мобильный и desktop layout **без переделки бизнес-логики и persistence**. Это архитектурная граница, а не обещание, что любую смену продуктового поведения можно выполнить только CSS.

```text
Presentation (Vue routes/views + design system + view-model adapters)
                  ↓  public typed actions / readonly state
Application (use-cases, local-first workflows, optimistic state, rollback)
                  ↓  ports
Domain (validation, rules, ACL intent, lifecycle, states, policy snapshots)
                  ↑  implements ports
Infrastructure (PB2 crypto/Identity, Dexie/OPFS, HTTP/Laravel, S3, camera)
```

**Обязательные правила:**
1. **Domain** не импортирует Vue/DOM/Router/HTTP/IndexedDB/crypto SDK. **Application** предоставляет типизированные команды и результаты (не ссылки на Vue-компоненты); local-first, durable commit, optimistic state, offline/retry/conflicts/rollback принадлежат use-cases. **Infrastructure** реализует ports. **Presentation** отображает readonly view-state и вызывает команды через **public feature API / view-model adapter**.
2. Vue `ui/` не импортирует `infrastructure/`, `database.ts`, raw `fetch`, `localStorage`, `crypto.subtle`, Laravel/S3/Matrix SDK или внутренние файлы чужого feature. Никаких прямых DB writes, серверных security decisions, TTL/permissions или encryption rules в шаблонах/компонентах. Весь IPC между модулями через `index.ts` + versioned DTO/ports, без циклов и глобальных god-stores.
3. Для каждого пользовательского сценария отдельно задать **типизированное состояние**, **команды**, и **сигналы статуса** (local-pending, syncing, synced, conflict, denied, locked, offline, expired, quota, failed). Только authoritative success → успех; UI не подменяет ACK анимацией или фикстурой.
4. У UI собственный **design system**: токены цвета/типографии/отступов/радиусов/тем/контраста, primitives Button/Input/Sheet/Dialog/Toast/Status, composable AppShell/Navigation/Workspace. Отдельные конфигурации mobile/desktop могут использовать одни и те же use-cases. Текущий визуальный вариант **заменяем и не считается окончательно принятым**.
5. Не скреплять UI-решениями camera/storage/Identity/Assignments. Перестройка маршрутов, sidebar, layout или темы не пересоздаёт аккаунт, не удаляет IndexedDB, не отбрасывает outbox, не перезапускает kernel и не продлевает TTL. Внутренние действия способны работать из **двух альтернативных UI-обёрток**, не имея знаний об их композиции.
6. Минимальная проверка при каждом новом модуле: headless unit/contract tests use-cases **без Vue**, тесты view-model state, import-boundary/cycle negative test, и проверка, что смена layout/темы/навигации не меняет данные и вызовы application. UI fixtures всегда обозначать явно, не имитировать действительную функциональность.
7. При необходимости визуального редизайна менять только `ui/`, tokens, shell, routing composition и адаптеры представления; domain/application/infrastructure не трогать, **пока не изменились функциональные требования**. Проверка исключений обязательна, если проект ещё имеет UI→infrastructure coupling: фиксировать это как defect, не воспроизводить в следующих Issues.

**Не создавать UI-framework “на всё будущее” заранее:** только реально используемые компоненты, ports и устойчивые контракты. Любой UI-слой должен оставаться production-grade, mobile-first/iPhone PWA, RU/EN, accessible, fast and offline-capable.

## 5. Review, status, release

| Метка исполнения | Что доказано | Что НЕ доказано |
| --- | --- | --- |
| `Implementation Ready` | Scope и upstream contract достаточны для кода | Merge/acceptance |
| `Implemented (Draft)` | Код и нужные тесты представлены в scope PR, собственный diff проверен | Компиляция, безопасность или production |
| `Verified` | Codex реально провёл требуемые проверки на полном окружении и приложил доказательства | Owner accepted/released |
| `Integrated` | Проверенный PR вошёл в main; новые ветки актуализированы | Реальный mobile acceptance |
| `Accepted` | Владелец принял согласованные сценарии на устройствах | Остальная система/release |
| `Released` | Полный release/security/backup/rollback gate пройден | Ничего не обещать сверх доказанного |

`Implemented` и `Verified` могут быть **дополнительными метками/полями PR/Issue**; не переименовывать насильно Project status и не ложно выставлять `Ready/Integrated`. Существующие Project состояния сохраняются; Codex приводит их в соответствие на финальной фазе.

UX milestone review полезен **раньше** финального этапа, если есть возможность, но отсутствие Codex preview или ещё не принятый внешний вид **не останавливает написание** следующих независимых/зависимых модулей в Phase I. Зафиксированные замечания UX обязательны к устранению **до Accepted/Released**, не означают отмену исходных API/сценариев. Никаких релизов/деструктивного тестирования без независимого review и безопасной среды.

## 6. Передача Codex и единый план финальной интеграции

После последней функциональной Issue ChatGPT передаёт:
- полный порядок Issue → `branch` → Draft PR → `base/head SHA`, зависимости, известные upstream corrections и `merge-base`;
- матрицу **реально выполненных** тестов и всех `NOT RUN`, scope/legacy evidence, миграции/rollback/TTL/crypto/ACL impact;
- список архитектурных исключений UI, открытых owner decisions, security/operational P0 risks, проблем на мобильных устройствах и дефектов;
- последовательный план merge, retarget и финального общего E2E.

**Codex** исправляет в исходных PR, самостоятельно проверяет зависимые PR и интегрирует. Если первый PR в цепочке критически повреждён, **сначала** исправляет его, затем переносит исправление в dependents; не маскировать неисправность финальным squash-коммитом. До завершения проверки **весь набор считается “Implemented, NOT VERIFIED”**, даже если отдельные сценарии работали в dev.

**Ничто здесь не снимает:** запрет force-push, прямого изменения `main` ChatGPT, авто-merge, работы в old repo, скрытого изменения утверждённого scope, лжи о тестах/производственной готовности или ослабления security/TTL/ACL.
