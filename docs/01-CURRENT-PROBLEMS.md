# 01. Почему текущий PhotoBunker пересобирается

**Статус:** диагностика + проектная мотивация, 2026-10-28. **Не** инструкция переписать всё с нуля.  
**Источник:** приватный `1troitsky/photobunker`, проверенный `main` @ `31ac3687e1a3c3cede14bd8f8122b9ab3c929534`; пользовательское наблюдение от 28 октября.

## 1. Что пользователь увидел в реальном приложении

Владелец сообщил: плохо пригодный к работе UI/UX; ожидание десятков секунд при открытии сообщений и разделов; запутанные состояния ключей; неработающая камера; нестабильность; разрыв между заявлениями о готовности и реальным продуктом. Оценка: 1/5.

Это **пользовательские наблюдения**, не подтверждённые нашими собственными замерами на том же телефоне. Их нельзя отменять результатами юнит-тестов.

## 2. Проверенные в исходниках факты

1. `apps/web/src/local/photos.ts`: `localPrototype = import.meta.env.DEV || VITE_LOCAL_PROTOTYPE === 'true'`. `views/CameraView.vue` использует этот флаг в разрешении запуска камеры и shutter. Обычная production-сборка без явного прототипного флага отключает камеру. Простое включение прототипного флага **не является безопасным исправлением**: legacy-прототип использует незашифрованное локальное хранилище, запрещённое release guard.
2. `apps/web/src/messages/store.ts` — около 2 412 строк; `MessagesView.vue` — около 1 499; `CameraView.vue` — около 1 256; `crypto/photos.ts` — около 1 707. Это признаки чрезмерного смешения ответственности, но само количество строк не является измерением дефектов.
3. В старом messenger запуск соединения Matrix, синхронизация и восстановление ключей связаны с жизненным циклом экрана. Это создаёт риск многократных дорогостоящих повторных подключений; реальные 40 секунд не были нами измерены.
4. Камера и ряд экранов до готовности вызывают удалённые загрузки и/или тяжёлую инициализацию. Следовательно, обещание «экран не ждёт сеть» не обеспечено архитектурно.
5. `compose.yaml` для web запускает Vite dev server; часть browser smoke ориентирована на dev imports. Успех dev-тестов не гарантирует работоспособность собранного production-клиента.
6. На дату аудита последние workflow runs GitHub Actions для исходного репозитория были красными; подробные логи были недоступны. **Причина падения CI не установлена.**
7. Laravel уже используется: `apps/api/composer.json` требует `laravel/framework: ^13.17`; PostgreSQL, S3-compatible Garage и Matrix разнесены по сервисам. Не следует заявлять, что весь проект был реализован без Laravel.
8. Унаследованный PIN приложения (`apps/web/src/app/pin-store.ts`) прямо заявлен как **UI-lock verifier**, а не шифрование данных в покое при компрометации браузерного профиля. PIN удаления и экстренные операции имеют отдельные механизмы; нельзя их бездумно объединять.

## 3. Корневая проблема

Проблема **не** в одном плохом компоненте и **не** только в отсутствии тестов. Прикладная логика, глобальные состояния, сеть, локальное хранение, криптография и интерфейс слишком тесно соединены. Поэтому:
- изменение одной функции несёт риск побочных эффектов в соседних;
- локальный экран не имеет стабильного независимого источника состояния;
- разработка каждого следующего сценария усложняет уже существующие;
- формальные тесты могут доказывать работоспособность функций по отдельности, не защищая пользовательский маршрут в release.

Решение не сводится к тому, чтобы разбить один файл на десять файлов или заменить фреймворк. Нужны **проверяемые границы ответственности и данных**, конкретный storage lifecycle и production-поведение.

## 4. Чего нельзя повторять

- Один огромный store или page как одновременно SDK-клиент, сетевой слой, очередь, криптография и UI.
- Direct API/IndexedDB/SDK calls из любого случайного компонента.
- Неформальные договорённости о слоях без автоматической проверки импортов.
- Подмена реальных encrypted/offline flows временными незашифрованными прототипами.
- Экран, который ничего не показывает до сетевого запроса.
- Разные правила работы с фотографиями в галерее, редакторе, браузере и карточке.
- Неограниченные дубликаты original/preview/thumbnail/version/export и фоновые «сироты».
- Заверения «готово» на основании unit/dev без production и пользовательских сценариев.
- Самовольное создание очереди Issues/PR до окончания обсуждения архитектуры.

## 5. Что можно переносить из старого проекта, но только после проверки

Laravel API и его модели доступа, спецификации и тест-векторы шифрования фото, server-side ограничения TTL/ACL, Photo Card/Browser contracts, логика заданий, маршруты и схемы данных. Перенос **не означает** копирование файла или сохранение его архитектуры. Каждый блок получает независимый аудит на соответствие новым утверждённым правилам, безопасность, расходы на хранение и обратную совместимость.

**Нельзя** переносить предположение «immutable original всегда»: владелец подтвердил противоположную цель для фото вне заданий, где обязательное хранение оригинала не задано.

## 6. Критерий новой архитектуры

Небольшое изменение политики хранения, редактора, права доступа или формата previews должно требовать изменений **в ограниченном числе мест**, не переписывать шесть модулей, не раскрывать чужие данные и не превращать ошибку API в сломанную навигацию.

Архитектурное решение обязано объяснять: кому принадлежит каждая сущность и байт, кто создаёт, кто может заменить, кто удаляет, что происходит при сбое посередине и как это автоматически проверить.
